# Decisions

| 2026-08-10 | `reserved_transaction_id` is a plan-identity value only, not threaded into `transaction_journal.py`'s actual transaction ID | Claude Code (design phase) | Pre-register the ID with the journal at emit time so apply-time execution is forced to reuse it | Building real pre-registration machinery in the journal is a materially larger, separately-scoped change (the journal's transaction ID is currently always generated at prepare-time, not accepted as an input); the audit-correlation value of a plan-carried UUID doesn't require that deeper integration | Recorded as an explicit out-of-scope item in change.yml; a future spec could thread it through if evidence shows the correlation gap matters in practice |
| 2026-08-10 | `--apply-plan` requires a separate `--yes` confirmation even against a completely unmodified, freshly-emitted plan | Claude Code (implementation phase) | Apply immediately once verification passes, matching how `--revision` already works today | The plan format is new and this is the first release of the feature; an extra explicit confirmation step costs little and gives an operator one more chance to notice something is wrong, consistent with `AI_HUMAN_INTERACTION.md`'s preference for explicit confirmation before destructive operations. The existing `--revision` path already requires `--yes` too (inherited from generic `archive`), so this is not actually a new pattern for the project | None; this is not a design gap, just documented here since it goes slightly beyond issue #255's literal acceptance criteria |
| 2026-08-10 | Documented `project archive` (the base command) alongside the plan workflow, even though documenting it was not itself in scope | Claude Code (documentation phase) | Document only `--emit-plan`/`--apply-plan` in isolation, with no base-command context | `project archive` had no prior documentation anywhere in `docs/en`/`docs/ja` (confirmed by search); documenting the plan workflow with zero context for the command it extends would be confusing and each doc page reads on its own. See design.md's "Known Gap Found During This Work" | None |
| 2026-08-10 | Root cause of #183 remains unaddressed by this change | Claude Code (scoping, per the originating issue's own text) | Attempt to reproduce/diagnose the original zero-byte failure as part of this change | #183's own investigation goals (root-cause reproduction, failure-injection tests around archive validation) are separate, larger, and explicitly out of scope for #254/#255/#256, which implement `todo.md`'s "add a reviewable plan workflow... without re-blocking production" item specifically. #183 stays open | #183 remains open; its own remaining investigation goals are unaffected by this change |
| 2026-08-10 | `selected_item_ids` is populated only from items carrying an explicit `id:` (or configured `id_key`) detail, reusing `command_archive`'s pre-existing `candidate_ids` computation unmodified; an item with no ID contributes nothing, so a workspace without `ids.auto` enabled (or with unlabeled items) can emit a plan with `"selected_item_ids": []` even though the dry-run text lists real candidates | Claude Code (found during live manual verification, after the primary 29-test suite passed) | Derive a universal per-item identity (e.g. `source:line` or a title-based fallback) so the field is never empty | Not a data-safety gap: `verify_selection_unchanged` is defense-in-depth layered *underneath* `verify_revisions_unchanged` and `verify_workspace_revision_unchanged`, which already guarantee byte-identical source files at apply time -- byte-identical input to the same deterministic filter necessarily reproduces the same candidate set regardless of whether `candidate_ids` happens to be populated. It is, however, a real reviewability/audit gap: an operator inspecting `plan.json` for such a workspace cannot see which items will be archived from `selected_item_ids` alone and must fall back to the separately-printed dry-run text. Fixing it well (a stable, collision-resistant identity independent of `id:`) is a small-looking but real design decision that the existing 29-test suite does not cover either way, and reusing the exact semantics `command_archive` already established for `candidate_ids` keeps this change's behavior consistent with a pre-existing concept rather than inventing a second, divergent notion of item identity | Recorded as a known limitation rather than fixed in this change, given the safety property is intact; a follow-up could add a title/line-based supplementary field for plans over ID-less workspaces if operators report the audit gap in practice |
| 2026-08-10 | Renamed "tamper detection"/"tamper check" to "self-consistency check" throughout code, error messages, and docs; removed the "share it" language from operator documentation | Claude Code (post-implementation `/security-review`, confirmed at 8/10 confidence) | Build real cryptographic authentication (HMAC with a locally-generated, persisted key, or a detached signature) so the hash genuinely resists a deliberate actor with plan-file write access | `plan_hash` is computed from and stored in the same file it covers, with no external key -- anyone who can edit the plan file can recompute a matching hash, so it was never actually tamper-resistant despite the original naming. The original docs' "review before applying -- share it, diff it, hold it" language implied a handoff/review workflow crossing a trust boundary, which is exactly the scenario where the naming's implied guarantee would matter and does not hold. Real authentication would require key generation, storage, and distribution -- explicitly out of scope per this package's own "no plan-signing key infrastructure" boundary (see the `selected_item_ids`/journal-registration entries above for the same size-of-scope reasoning) -- so the proportionate fix is honesty: accurately describe what the check catches (accidental corruption/hand-edits) and instruct operators to keep plan files under their own control between emit and apply, the same trust level as any other local input to this command, rather than implying a security boundary that doesn't exist | If evidence later shows operators need to hand plans across a genuine trust boundary (e.g., a different reviewer applying a plan someone else emitted), a future change should add real signing rather than relying on plan_hash for that purpose |
| 2026-08-10 | A related security-review candidate finding (unscoped `sources`/`destination` paths taken verbatim from a loaded plan, with no check that they lie within the resolved workspace manifest) was investigated and not fixed | Claude Code (post-implementation `/security-review`, false-positive-filtering pass, excluded at 2/10) | Add workspace-scope validation to `_project_archive_apply_plan` for `sources`/`destination` paths loaded from a plan | Confirmed by reading `archive_safety_v3.py`'s `_archive_preflight`: the existing, pre-this-change `--revision`-flag path already accepts an arbitrary `--dest` and explicit source paths from the same trusted local operator with no workspace-scope validation -- that guarantee only ever applied to the *implicit* default-destination case. `--apply-plan` inherits this pre-existing characteristic rather than introducing a new bypass; per the filtering pass's own scope discipline (only act on security implications newly introduced by this change), this is not this change's defect to fix | Recorded as a pre-existing design characteristic of `project archive`, not a gap in this change; a future change could add workspace-scope validation to both the `--revision` and `--apply-plan` paths together if evidence shows it's needed |
