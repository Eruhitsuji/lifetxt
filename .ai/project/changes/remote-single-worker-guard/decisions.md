## Observed but out of scope

Live verification found that `uvicorn.config.Config` itself already reads `WEB_CONCURRENCY` from the environment (`uvicorn/config.py:352-353`) and sets `self.workers` accordingly, independent of any lifetxt code. Since `lifetxt serve` calls `uvicorn.run(app, host=host, port=port)` with an in-memory app *object* (not an import string), uvicorn cannot actually honor `workers > 1` this way and exits with `WARNING: You must pass the application as an import string to enable 'reload' or 'workers'.` and a non-zero exit code -- confirmed to reproduce identically with `remote.enabled` entirely absent, so this is a pre-existing `lifetxt serve` behavior, not something this change introduces or regresses. This change's guard actually improves the situation for the common case (`remote.enabled=true`, no override): it now raises a clear, lifetxt-specific error *before* uvicorn's confusing generic warning is ever reached. The override path (`remote.allow_multi_worker=true`) is intended for `create_app()` being launched by an external multi-worker-capable manager (gunicorn, `uvicorn --workers N` invoked with an import string), not for `lifetxt serve` itself, which cannot multi-worker regardless of this guard. Recorded here as a found-but-out-of-scope gap, not fixed by this change: `lifetxt serve` crashing with a confusing uvicorn-level warning whenever `WEB_CONCURRENCY` happens to be set in the operator's environment, with or without Remote Safe Mode enabled at all, is a separate CLI-usability papercut filed as its own follow-up: #172.

## Scoping note

The broader "P1: Remote Safe Mode follow-up" and "P1: Remote Safe Mode and Remote Workspace Access" sections of `todo.md` list many further hardening items (durable multi-worker session backend, real TLS/browser/proxy integration evidence, audit-log hardening, authorization matrices, SSE/WebSocket transport). This change deliberately implements only the narrow, well-bounded item `todo.md` line 72 itself names as the lighter alternative to a full durable backend: "explicit single-worker enforcement." The rest remain open, unattempted by this change, and are candidates for their own future specs -- building a real shared backend, in particular, is a materially larger effort that a durable-backend spec should own, not something this change should absorb as "just one more thing."
