# Decisions

| Date | Decision | Owner | Alternatives | Reason | Follow-up |
| --- | --- | --- | --- | --- | --- |
| 2026-08-22 | `assist` profile's write allowlist is exactly `stage_proposal`, nothing else | Repository owner (via AskUserQuestion, before design) | Also allow non-destructive quality-of-life writes (`ack_message`, `snooze_message`, `timer_start`/`timer_stop`, `capture_item`); defer the decision to the design phase | Matches #500's own explicit "keep assist intentionally small" principle; every `assist` write goes through a human-reviewed acceptance step, which broader writes would bypass | Widening the allowlist is out of scope for this change; would need its own follow-up issue with fresh justification |
| 2026-08-22 | `--read-only` becomes an alias for `--profile read`, normalized inside `McpContext.__init__` | Repository owner (via AskUserQuestion, before design) | Keep `--read-only` and `--profile` as two independent, separately-enforced flags | One authorization model is easier to reason about and test than two overlapping ones; normalizing inside `McpContext.__init__` (rather than in the CLI layer) means direct programmatic construction (existing tests, any future non-CLI caller) also gets the new dispatch-level protection automatically | None |
| 2026-08-22 | Escalate to assurance level High / change_type Security, with a full change package and cc-sdd spec | Claude (design phase), per this project's `ASSURANCE_LEVELS.md` escalation rules | Treat as an ordinary Standard-assurance task | This changes the MCP server's authorization boundary (`AI_HUMAN_INTERACTION.md`'s "authentication or authorization change" requires explicit human approval); matches the precedent set by `cap-remote-single-worker-guard` for comparable session/auth-adjacent hardening | Independent security review and Merge Authority approval required before this branch's work merges into main, per `human_approvals_required` in `change.yml` |
| 2026-08-22 | Enforce identically at both `tools/list` and `tools/call`, via one shared allowlist function | Claude (design phase) | Filter only at `tools/list` (trust the client not to call an unlisted tool); filter only at `tools/call` | Filtering only one path leaves the other unenforced, contradicting the fail-closed requirement that a client cannot bypass the profile by calling a tool it was never shown | None |
| 2026-08-22 | Give `tool_schemas()` no new parameter; add a separate `filter_tool_schemas_for_profile(schemas, profile)` and filter in `handle_request` instead | Claude (implementation phase, found by live tracing before writing the fix) | Add an optional `profile` parameter directly to `tool_schemas()`, as originally designed | Live tracing found `lifetxt/__init__.py` unconditionally wraps `mcp.call_tool`/`mcp.tool_schemas`/`mcp.handle_request` at import time from four other modules (`surface_runtime.py`, `surface_runtime_compat.py`, `remote_contracts_v6.py`, `ticket_project_surfaces.py`), each redefining `tool_schemas()` with zero parameters. A parameter on the base function would raise `TypeError` the moment `handle_request` calls the live (fully wrapped) name -- confirmed by reproducing the exact `TypeError` before switching approach. See `.kiro/specs/mcp-permission-profiles/research.md` for the full trace | None; regression-tested via `test_filter_tool_schemas_for_profile_is_independent_of_tool_schemas_signature` and the full existing suite (`tests.test_surface_runtime`, `tests.test_mcp_expansion`) passing unmodified |
| 2026-08-22 | Move the `--read-only`/`--profile` conflict check into `McpContext.__init__` rather than only `from_args` | Claude (implementation phase, found while writing tests) | Keep the check only in `from_args`, as originally designed | A test constructing `McpContext` directly (bypassing the CLI) with `read_only=True, profile="assist"` did not raise, which would have let direct callers create a contradictory, actually-dangerous state: `self.profile` stays `"assist"` (so `_profile_allowed_tools` would treat `stage_proposal` as allowed) while `self.read_only` becomes `True` (so every `_require_writable`-based handler guard, and the outer monkeypatch layers' own read-only checks, would treat the connection as fully read-only) -- an inconsistency between the two enforcement layers rather than a clean single state. Centralizing the check in `__init__` protects every caller, not only the CLI | None |
| 2026-08-22 | Scope the Unified Inbox proposal store (`inbox.proposals_file`) to each test's own temp directory in the test helper | Claude (implementation phase, found via a real full-suite regression run) | Leave the test helper as-is | `lifetxt.inbox`'s default proposal store path (`.cache/lifetxt/proposals.json`) is resolved relative to the process's current working directory, not to any per-test workspace, when no `inbox.proposals_file` is configured. New tests that called `stage_proposal` without setting this key wrote real, persistent entries into the actual repository checkout's `.cache/lifetxt/proposals.json` (confirmed by running the full suite from the repository root and finding four unrelated, pre-existing Command Center/Today-view/Web-API tests fail because they observed those leaked pending proposals). Fixed by adding `inbox.proposals_file` to the test helper's per-test config, matching the existing pattern already used for `timer.state_file`; the stray file was deleted and confirmed absent from `git status` (already covered by the repository's leading-`.*` `.gitignore` rule, so this was local pollution, never a risk of being committed) | Live ad-hoc verification scripts run directly from the repository root during this session have the same underlying behavior (this is `lifetxt.inbox`'s pre-existing, unrelated default), so any future manual `stage_proposal` verification from the repo root should pass an explicit `inbox.proposals_file` or run from a scratch directory |
