| 2026-08-09 | Git-based update only; no package-manager path | Claude Code (requirements phase) | Publish to PyPI first, then use pip's own upgrade mechanism | lifetxt has no PyPI distribution and none is being added by this change; the only documented install method is `pip install -e .` from a git clone, so git is the only mechanism that can actually exist today | A future PyPI release would be a separate, larger change; this command would need a second code path added at that time, not replaced |
| 2026-08-09 | Dry-run by default; `--yes` required for any real change | Claude Code (requirements phase), per explicit repository owner instruction | Apply immediately, prompt interactively for confirmation | Matches the mandatory safety-rail instruction this item was scoped under; a non-interactive default (no prompt) keeps the command scriptable while still requiring an explicit, unambiguous flag rather than a keypress that could be muscle-memoried past | None |
| 2026-08-09 | Only `git fetch` + `git merge --ff-only`; never reset/rebase/force-push | Claude Code (design phase) | `git pull --rebase`, `git reset --hard <target>` | `--ff-only` is git's own built-in refusal mechanism for anything unsafe -- it cannot rewrite history or discard commits by construction. `reset --hard` would silently discard any local commit ahead of the target (impossible given the dirty-tree check, but still a strictly more dangerous primitive with no benefit here); `rebase` rewrites history unnecessarily for what is always meant to be a simple forward move | None |
| 2026-08-09 | Never run `pip install` or any build step after updating | Claude Code (design phase) | Automatically run `pip install -e .` after a successful fast-forward | Running the freshly-fetched commit's build backend is a materially larger trust/execution boundary than fetching and fast-forwarding text; `update`'s own safety story (git-only, no code execution) would not hold if it then executed arbitrary setup code from the commit it just fetched | Recorded as a known limitation; the "updated" message names the manual follow-up step instead |
| 2026-08-09 | `--repo`/`update.repository` only selects the GitHub API ref-name lookup, never the git remote URL | Claude Code (design phase) | Derive the git fetch URL from `--repo` (`https://github.com/<repo>.git`) | Keeps the trust boundary identical to a manual `git fetch`: the remote a user's `update` command talks to is always the remote *they* configured, never a URL assembled from a config value or CLI flag. A malicious `update.repository` can at worst cause a failed fetch of an unknown ref name against the user's own trusted remote | None |
| 2026-08-09 | Reject a ref/remote value beginning with `-` before it reaches any `git` argv | Claude Code (design phase), found during design review of the resolved-ref data flow | Rely on git's own argument parsing to reject or misinterpret it | A maliciously-named tag (e.g. `--upload-pack=...`) could otherwise be misread as a git command-line option instead of a ref name -- a known class of git argument-injection issue. Rejecting it outright, before constructing the argv, closes the class rather than hoping git's own defenses (`--` end-of-options, when present) are used consistently at every call site | None |
| 2026-08-09 | Decode git subprocess output as UTF-8 with `errors="replace"`, not the platform locale codec | Claude Code (implementation), found via live verification | Leave `universal_newlines=True` with the platform default codec | Live verification against a real Windows ja-JP-locale directory tree crashed with `UnicodeDecodeError` inside `subprocess.run`'s reader thread when git's output contained a byte not representable in cp932. This is a real, reproducible robustness gap discovered during this change's own verification, fixed before the change was ever proposed for review | None |
| 2026-08-09 | Escalate to assurance level High / change_type Security, with a full change package and cc-sdd spec | Claude Code (task decomposition), per explicit repository owner instruction to treat session/auth/write-adjacent hardening in this batch as needing individual design confirmation, and per the item's own scoping note that this specific command was flagged not-recommended and accepted anyway | Treat as an ordinary Standard-assurance batch item | This is the only lifetxt command that mutates the git working tree the running install lives in, with no release pipeline and no rollback story beyond git itself. `.ai/managed/core/ASSURANCE_LEVELS.md` requires escalation for destructive-operation-adjacent and unclear-design-decision risk factors, both present here | Human security/implementation review and Merge Authority approval still required before merge to main, per `human_approvals_required` in `change.yml` |

## Explicitly not-recommended, implemented anyway

During batch scoping, this item was flagged by the implementing agent as **not recommended**: the project has no PyPI distribution or release pipeline, and no rollback story beyond git's own history. The repository owner selected it anyway, alongside every other proposed CLI item, without further discussion of the risk framing at that time. This change package implements it with every safety rail described above as the condition under which that acceptance is honored -- the design deliberately narrows scope (git-only, fast-forward-only, no code execution, dry-run default) rather than building the more ambitious "auto-update and reinstall" command a user might picture from the word "update".

## Scoping note

`todo.md`'s CLI-enhancement roadmap items covered system diagnostics (`doctor`), version reporting (`--version`), and an update mechanism as a group. This change is the last of that group; `doctor`/`--version`/`update-check` (and `update-check`'s own configurable-repository follow-up) landed earlier in the same `cli-web-multiday-enhancements` batch, all reusable by this change without modification.
